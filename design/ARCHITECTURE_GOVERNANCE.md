## 1. 核心原则

### 1.1 设计先行原则

**所有架构修改必须先完成设计文档，未经批准不得修改代码。**

这是唯一正确的开发流程：

```
┌─────────────┐
│  需求提出   │  ← 用户/系统提出修改需求
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  设计文档   │  ← 必须先生成完整设计方案
│  (DESIGN)   │    包含：问题分析、方案对比、
│             │    风险评估、测试计划
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  用户批准   │  ← 明确批准 ("批准执行")
│ (APPROVAL)  │    口头/文字确认均可
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  代码实现   │  ← 此时才能开始写代码
│ (CODING)    │    严格按设计文档执行
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  测试验证   │  ← 单元测试 + 集成测试
│  (TEST)     │    所有测试必须通过
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  部署上线   │  ← 正式生效
│ (DEPLOY)    │
└─────────────┘
```

### 1.2 禁止行为

**以下行为被严格禁止：**

| 禁止行为 | 后果 |
|----------|------|
| 未经批准直接修改代码 | 系统不稳定、技术债务 |
| 先实现后补文档 | 设计缺陷、无法追溯 |
| 边设计边编码 | 方案不周全、返工 |
| 口头方案直接执行 | 误解、遗漏 |
| 绕过批准流程 | 架构腐化 |

## 2. 设计文档规范

### 2.1 文档命名

```
design/
├── README.md                    # 设计文档索引
├── architecture_v3.md           # 总体架构
├── auto_recovery_design_v2.md   # 自动恢复系统
└── feature_YYYY_MM_DD_name.md   # 新功能设计
```

### 2.2 文档结构

每个设计文档必须包含：

```markdown
# [功能名称] 设计方案

## 1. 问题分析
- 当前问题是什么
- 为什么要修改
- 不改会怎样

## 2. 需求分析
- 功能需求
- 非功能需求 (性能/稳定性/安全)
- 约束条件

## 3. 方案设计
### 3.1 方案对比
| 方案 | 优点 | 缺点 | 风险 |
|------|------|------|------|
| A | ... | ... | ... |
| B | ... | ... | ... |

### 3.2 推荐方案
- 详细设计
- 架构图
- 接口定义

## 4. 风险评估
- 技术风险
- 回滚方案

## 5. 测试计划
- 单元测试
- 集成测试
- 验收标准

## 6. 实施计划
- 步骤分解
- 时间估算
- 依赖关系

## 7. 批准记录
- 批准人: [用户名]
- 批准时间: [日期]
- 批准方式: [口头/文字]
```

### 2.3 批准格式

**用户批准的标准表述** (满足任意一种即可)：

```
✅ "批准执行"
✅ "批准"
✅ "可以"
✅ "动手吧"
✅ "开始"
✅ "做吧"
✅ 👍 / ✅ / OK
```

**未批准的表现** (禁止执行)：

```
❌ "看看" / "看看方案"
❌ "考虑一下"
❌ "待定"
❌ 无回应
❌ "再想想"
```

## 3. 变更类型与流程

### 3.1 变更分类

| 类型 | 定义 | 设计文档 | 批准要求 |
|------|------|----------|----------|
| **架构变更** | 影响核心组件、接口、数据流 | 必须 | 必须 |
| **功能新增** | 新增模块、功能 | 必须 | 必须 |
| **配置修改** | 参数调整、开关切换 | 可选 | 建议 |
| **Bug 修复** | 修复现有功能 | 可选 | 建议 |
| **文档更新** | 纯文档修改 | 无需 | 无需 |

### 3.2 紧急修复流程

**生产事故时的例外流程**：

```
事故发生
    ↓
立即修复 (最小改动)
    ↓
事后24小时内补设计文档
    ↓
复盘会议
```

**注意**：紧急修复只能用于生产故障，不能用于新功能。

## 4. 执行检查清单

### 4.1 我 (AI) 的自我检查

每次架构修改前，我必须确认：

- [ ] 设计文档已生成
- [ ] 文档包含完整方案
- [ ] 已获得用户明确批准
- [ ] 批准表述符合标准
- [ ] 未擅自提前写代码

### 4.2 违规处理

**如果我违规**：
1. 立即停止当前工作
2. 向用户报告违规行为
3. 回滚已修改的代码
4. 重新走完整流程
